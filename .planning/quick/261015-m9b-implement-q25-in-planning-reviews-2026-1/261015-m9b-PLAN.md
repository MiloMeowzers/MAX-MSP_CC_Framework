<planner_decisions>
The report leaves these choices open. Each was measured at planning with scratch prototypes (numbers in `<reference_data>`).

1. **Detector = normalized ACF with multi-period refinement.** The spec's peak rule (first peak > 0.9*max after the first zero crossing) fixes the 4009 Hz and octave errors. Single-peak parabolic interpolation alone is not enough: naive saw/pulse/square waves have corner-shaped NACF peaks, which biased the prototype by up to 2.84 cents (926 Hz) and 1.37 cents (440 Hz saw), failing "440 Hz saw reads 440". Re-locating the peak at 2T, 4T, 8T, ... and dividing by the multiple cut the worst error to 0.05 cents across sine/saw/pulse/square 50-1000 Hz. The inspection window becomes [40 Hz, 4 kHz] so 50 Hz has margin. scipy.signal.correlate (method fft) is kept, so the documented numpy+scipy dependency stays true.
2. **`bore_only` is removed (spec option "or remove it").** Under constant drive it settles to DC 0.324 at every setting. A single impulse at the default cone_loss 0.85 decays to tail AC RMS 3e-10..1.3e-3, mostly below the 1e-4 floor, and the ring-down read an octave low at 440 Hz with cone_loss 0.95-0.99. A pitch-locked periodic drive would measure the drive, not the bore, and pass by construction. None of these is a meaningful pre-flight, and nothing gates on bore_only. TECHNICAL.md:616 and max-dsp-agent SKILL.md:336 still list it; rule 8 protects both, so they go to SUMMARY doc impact.
3. **The v041 regression verdict changes, and the change strengthens the test.** Under the fixed detector the v0.4.1 mirror is DC-only (AC std 1e-4..2e-4) for bell_bright < ~0.7. Old code read that DC as 4009 Hz (+5022 cents), so the old `mode_competition` at step 0 was the H1 artifact; the mirror then jumps to ~1028 Hz (+2643 cents) at step 22. After H4 the honest verdict is `no_oscillation` at step 0. The test asserts that verdict plus the >50-cent mode jump in the later measurements. The mirror is not changed.
4. **Param validation covers sweep_param AND base-param keys** on the topology path (H4: "topologies declare params and reject unknown ones"); a misspelled base param is the same silent no-op. `mirror=` callables are dev-authored and declare nothing, so they are not validated, and the README says so.
5. **Port scope = the loop plus everything feeding it deterministically.** Included: breath smoothing (attack_time/release_time), 30 Hz Param smoothing, register bias, phase-delay compensation, allpass with frac in [0.1, 1.1), DC-blocked lossy cone reflection, Bernoulli reed + gate, post-loop reed BPF, body formant, bell LPF, output trim 0.25. The modulation/noise layers are fixed at their off values: vibrato FM and onset drift (vib_depth 0, drift_on 0), tremolo (vib_amp 0), breath noise (noise_amt 0), chiff (chiff_amt 0), tongue (tongue_trig 0). At those values the codebox output is bit-identical to the port, so exact genrun parity is possible. Because those layers are undeclared, sweeping them raises TopologyError instead of silently passing. Params are clamped to their codebox min/max, as gen~ does. `cone_loss` stays a declared sim knob (default 0.85 = the codebox constant) because existing callers pass it.
6. **Parity lives in the D-07 gate file**, so the gate fails as soon as the topology and the live codebox diverge (H3: the gate passed without testing the shipped loop). Behaviour change: any later DSP edit to bassoon.gendsp blocks the bassoon gate until the topology is re-ported or the fixture is skip-marked (D-10). SUMMARY flags it.
7. **Failing shipped-model sweeps are `xfail(strict=True, raises=AssertionError)` with the measured verdict as the reason.** Body assertions stay `verdict == "pass"` with default thresholds. Strict means a future fix turns them XPASS, which fails, so the marks must then be removed. This keeps the suite green (rule 4) without loosening anything, and the gate keeps blocking on parity, bell_bright, 58.27 Hz and any newly failing sweep. Marks follow the Task 3 measurement, never the planning expectation: bore_damp at 58.27 Hz sits only 0.31 cents under the limit, so it gets a strict xfail like any other sweep if it measures as failing. Whether to drop the marks so the gate hard-blocks every bassoon save is a user decision; SUMMARY offers it.
