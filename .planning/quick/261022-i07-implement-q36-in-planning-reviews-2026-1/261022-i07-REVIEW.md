## Warnings

### WR-01: Semantic diff misses cord order/hidden/color, I/O counts, and presentation_rect: "no changes" for a real write

**File:** `src/maxpat/patch_diff.py:69-72, 270-293, 321-324, 429-439`
**Issue:** `_cords` keys a cord only by `(src, outlet, dst, inlet)`, and `cord_rerouted` compares only `midpoints`. The patchline `order`, `hidden` and `color` fields are never compared, even though the Patcher tracks and writes all three (`patcher.py:51, 127, 159-160`). On boxes, `numinlets`, `numoutlets` and `outlettype` sit in `_STRUCTURAL_KEYS`, so they are left out of `attrs`, but no other entry kind reports them. `presentation_rect` is also left out of `attrs`, and `_presentation` throws it away when `presentation` is off.

Reproduced: a diff that changes a patchline's `order` 0→1, adds `hidden: 1`, changes a box's `numoutlets` 2→3 and changes a non-presentation box's `presentation_rect` renders `'no changes'`. `order` decides fan-out execution order (Rule #3), so this is a semantic change, not a cosmetic one.

`EditSession.__exit__` decides whether to write by comparing text, not by the diff. A session that only changes these fields therefore writes and commits (`session.saved` True), while the "what changed" output that `/max-iterate` step 18 shows the user, and that the Q39 `--fix` preview depends on, says nothing changed.
**Fix:** Report every changed patchline key, and make sure no box key can drop out unseen:
```python
# _cords: keep the full patchline; then for common keys
for key, pl in new_cords:
    ...
    changed = _changed_keys(old_first[key], pl,
                            frozenset({"source", "destination", "midpoints"}))
    if changed:
        add("cord_attrs", None, _cord_label(key), None, changed)

# _STRUCTURAL_KEYS: drop numinlets/numoutlets/outlettype (let them show as attrs),
# and compare presentation_rect even when presentation is off:
def _presentation(box):
    rect = box.get("presentation_rect")
    return (bool(box.get("presentation")), tuple(rect) if isinstance(rect, list) else None)
```
Also add a test for this invariant: `format_patch_text(new) != original_text` implies `bool(diff)`, run over every tracked patch with a mutated cord `order`.

### WR-02: /max-iterate recipe bumps versions.json inside the with-block, so the retry path double-bumps

**File:** `.claude/commands/max-iterate.md:97-112, 139-142`
**Issue:** The step-14 snippet calls `bump_version(...)` inside `with session as patcher:`. `bump_version` writes `versions.json` right away (`project.py`, `versions_file.write_text`). The save gate and stale check run afterwards, in `__exit__`. When the exit raises:
- `StaleFileError`: the doc says "re-run the session". Re-running the documented snippet calls `bump_version` a second time, so the version is bumped twice.
- `PatchValidationError`: the doc says "reuse the stored `new_version` and do not bump twice". But the same doc says a with-block lives in ONE Python process and cannot span tool calls, so the stored variable is gone when the script is re-run, and the snippet as written bumps again anyway.

In both cases `versions.json` can claim a version whose patch was never saved (refused and then abandoned).
**Fix:** Work out the version without writing it, embed it inside the block, and persist the bump only after a successful save:
```python
new_version = next_version(project_dir, "patch")      # pure read (add helper if absent)
session = edit_patch(path)
with session as patcher:
    ...edits...
    update_version_comment(patcher, new_version)
if session.saved:
    bump_version(project_dir, "patch", description, files_changed=[path.name])
print(session.diff.render())
```
Or, at minimum, document that a retry must read the current version from `versions.json` and skip `bump_version` when it already matches.

### WR-03: All writers switched to atomic replace (new inode) without MAX confirmation

**File:** `src/maxpat/hooks.py:139-152`
**Issue:** `_write_and_sync` used to rewrite the file in place. It now goes through `atomic_write_bytes`: a temp file, then `os.replace`. This change covers `save_patch_roundtrip`, `write_gendsp` and `write_js` alike (locked decision), but the docstring and docs present it as already safe for MAX ("so Finder/MAX see the change"). Every save now gives the file a new inode. Three effects need checking or noting:
- A watcher bound to the old inode (kqueue/vnode style), such as `js @autowatch 1` reloading a script that `write_js` just rewrote, or MAX's open-document change detection, may stop firing after the first replace. Nothing in the range or in memory confirms either behavior in MAX 9.2.
- Hard links to the patch are broken silently.
- macOS xattrs (Finder tags, `com.apple.FinderInfo`) are dropped. The docstring admits this one.

Project convention (CLAUDE.md, proven-forms tiers) treats behavior that has not been confirmed in MAX as pending.
**Fix:** Record this as pending a MAX check in SUMMARY/proven-forms. Test it with max-bridge: an open patch plus a `js @autowatch 1` script, rewritten twice through `write_js`, and the reload checked both times. Until then, either keep an in-place fallback for `write_js`, or soften the docstring and doc claims in `shared-capabilities.md:282` and `hooks.py:40-41`.

## Info

### IN-01: Touched-only contrast skips untouched text whose background a session changed

**File:** `src/maxpat/edit_session.py:115-119`, `src/maxpat/aesthetics.py:598-599`
**Issue:** Adding or moving a panel puts the panel in `only_ids`, but panels are skipped. Text boxes that are now sitting on the panel are never re-resolved, so a session can save unreadable text, and "Low contrast text" is only a warning, so the gate does not stop it. Boxes added inside subpatchers are also never covered (top level only). This is documented and fits locked decision D-03, but the gap is easy to close without changing the decision's intent.
**Fix:** When a touched panel exists, add to `only_ids` the untouched boxes whose `resolve_effective_background` result differs between the baseline panel layers and the current ones.

### IN-02: Unused `os` import kept only so tests can monkeypatch the global `os.fsync`
