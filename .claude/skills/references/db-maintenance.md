# Object Database Maintenance

Maintainer detail for `.claude/max-objects/`; CLAUDE.md keeps the one-line rules. Read this before editing `.claude/max-objects/` data (domain files, `overrides.json`, `groups.json`, `aliases.json`, `idioms.json`, `version_io.json`) or re-syncing after a Max update.

**`min_version` is always a string** (`"8"`, `"8.1"`, `"9"`, `"9.2"`; Q38 migrated the whole DB, and the extractors and the sync tool write strings). A float would turn 9.10 into 9.1; compare through `parse_version` in `src/maxpat/db_lookup.py`.

## Supplementary files: merge and inheritance semantics

- **`overrides.json`** -- Expert corrections that take precedence over extracted data. Merged per port: an override's `inlets`/`outlets` array sets the count, and each port replaces only the keys it sets, so base digests, `hot` flags and port types survive (generator placeholder digests and an empty `type` on a control port never replace base values; `{"id": N}` inherits the base port). Other keys replace whole; keys are canonicalized through `aliases.json`, and an unknown or duplicate key fails at load. A corrected entry carries an `_evidence` comment key (the refpage, help box or bundle source the values come from); keys starting with `_` are comments, never data.
- **MC outlet flavour** -- every MC-family signal outlet in `overrides.json` is typed the way MAX saves it in the bundle help: `multichannelsignal`, except the outlets MAX saves as plain `signal` (`mc.sum~`, `mc.unpack~`, `mc.channelcount~` 1, `mc.midiplayer~` 0, `mc.op~` 0, `mc.playlist~` 1, `mc.record~` 0, `mcs.groove~` 1, `mcs.selector~` 0). `db_lookup.saved_outlet_type()` emits the saved spelling and `get_outlet_types` uses it; validation treats both flavours as signal.
- **`variable_io_rules.trailing_inlets: K`** (non-negative int, validated at load) -- with arguments, the last K inlets map to the DB's last K entries and every leading inlet repeats DB inlet 0: `record~ buf 2` (K 2) is (signal, signal, start, end). `K == 0` (`sfrecord~ N`, `jit.catch~ N`) makes every inlet repeat inlet 0. `ObjectDatabase.resolve_inlet(name, inlet, args, *, count=)` applies it (Layer 3 resolves the destination inlet through it, with the box's saved `numinlets` as `count`).
- **Shipped signal inlets** -- `ObjectDatabase.is_shipped_signal_inlet(dst, inlet)` is True when any shipped help cord (`idioms.json`) feeds that inlet with a signal; Layer 3 then accepts a signal into it from every source. A guard test keeps every shipped signal idiom off a control-only DB inlet, and no unreviewed placeholder inlet may remain on a `~` object.
- **`inlet` / `outlet`** boxes are 0 inlets / 1 outlet and 1 inlet / 0 outlets in the DB (what MAX saves); their saved outlettype mirrors the parent cord, so the help-io oracle does not compare it (`tools/help_io.py` `CONTEXT_TYPED`).
- **`groups.json`** -- Inherited group names: MC wrapper methods/attributes (refpage `<mcwrapper>`), shared Jitter methods and OB3D/MOP/geometry attributes (refpage `<jittermethodlist>`/`<jitterattributelist>`, typed from the group pages), and thispatcher's help-patch selectors. Written only by `tools/sync_max_bundle.py --apply groups`, merged at call time by `ObjectDatabase`, never copied into domain files.

- **`aliases.json`** -- the 12 hand aliases plus the bundle's `max objectfile` shortcuts (Q38): the 13 `mc.wrapper~` shortcuts (`mc.times~` -> `mc.*~`), `hslider` -> `slider`, 31 `list.*` -> `zl.*`, 97 `jit.op` shortcuts (`jit.+` -> `jit.op`) and 90 Vizzie short names (`4mixr` -> `vz.4mixr`). The other unresolved objectfile names (`python3 tools/sync_max_bundle.py` lists them) stay unaliased: outside those groups, no candidate, or help boxes that disagree. The 11 file-basis `mc.*` names (`mc.meter~`, `mc.plugout~`, ...) are mono externals reading their own name with no help evidence for their I/O, so they are not aliased to `mc.wrapper~` targets.

## Merging audit proposals into `overrides.json`

`OverrideMerger` (`src/maxpat/audit/merger.py`, the audit CLI's `--merge` step) merges only proposals for names that have a base domain entry. A proposal with no base entry is skipped and reported in `merger.skipped` as `NO_BASE_ENTRY` (it is never written as an inactive `_note`). New keys use the canonical name; when an alias and its canonical name are both proposed, the canonical spelling wins and the other is reported as `DUPLICATE_OF <canonical>`. Before writing, `write()` rehearses an `ObjectDatabase` load of the merged file against a scratch root; if the load fails it raises `OverridesLoadError` and writes nothing. `--merge` prints the skipped proposals and returns 1 on a rejected write (`OverridesLoadError` or `OverridesChangedError`); a no-op merge leaves the file byte-identical.

## Shipped idioms (`idioms.json`)

`tools/sync_max_bundle.py --apply idioms` mines every cord the installed bundle's help patches ship (`*.maxhelp` under `Contents/Resources/C74` only, never user packages; gen~ / rnbo~ internals skipped, like the help-box oracle) and records it as `pairs[<source>]` items `"<outlet> <signal|control> <destination> <inlet>"`. The class is the source box's own saved `outlettype` at that outlet, so an argument-dependent layout (`sfplay~` vs `sfplay~ 2`) does not match. Endpoints that are structural (inlet/outlet/patcher/bpatcher), content-defined (`p`, `poly~`, `js`, `gen~`, ...), `*codebox*` or carry an embedded patcher are excluded. The write is additive (a committed pair is never dropped), canonical and idempotent; `ObjectDatabase.is_shipped_idiom` canonicalises both names through `aliases.json`. Validation Layer 3 and `replace_box_safe` skip type/role checks for a listed cord -- index bounds, missing boxes and malformed cords are always checked, and Layer 4 value/topology rules (gain safety, feedback, unterminated chains) are not pair checks and are untouched.

## Per-version I/O (`version_io.json`)

`--apply version-io` records, per name, the I/O changes shown by bundle help boxes saved by different Max builds (`patcher.appversion`): boxes of one name and argument list must form a strict version-ordered partition of their `(numinlets, numoutlets)` (every segment's last version before the next one's first), every argument group of a name must agree on the deltas, and a name with interleaved versions is only counted (ambiguous). The file is regenerated wholesale -- it is mined evidence, not curation; review the dry-run's `+added -removed ~changed` counts before applying. Max 9.2.0 gives 8 names (`live.meter~`, `metro`, `midiformat`, `midiparse`, `mousestate`, `poke~`, `preset`, `twist~`); `metro` and `twist~` come from help saved by a 9.3 build (`newer_than_installed`, ignored by validation until the installed Max catches up). `vst~` and `retune~` show one I/O in every bundle help box, so they are not recorded (their DB gaps were help-vs-DB mismatches fixed by Q11). `validate_patch(patch, target_version="9.0")` reads it, warnings only.

## Empty I/O entries

**Verify lookup results have non-empty I/O.** Some DB entries (especially in `packages/`) were extracted with `inlets: []` and `outlets: []`. `lookup()` returns these as real hits, but the patch builder cannot connect them — they are indistinguishable from "missing" at the connection site. Treat empty-I/O entries as missing and populate them via `overrides.json`. Use `db.audit_empty_io()` to enumerate them. When a user reports an object "missing" you've used before, check both `lookup()` returns AND inlet/outlet lengths -- not just `exists()`. The `by_source` key of `audit_empty_io()` enumerates empty-I/O gaps per domain/package file. `lookup()` warns only when BOTH sides are empty — a zero-outlet sink (`dac~`, `print`, `send~`) or zero-inlet source (`begin~`) is legitimate DB data, not a gap, and `db.audit_half_empty_io()` enumerates those one-side-empty entries as `sinks`/`sources`. Before adding an object fresh to a domain file, search the `packages/` subdirectories and `overrides.json` first — it may already exist with partial data worth merging (same-named package entries can shadow populated core entries). Before declaring an object unknown, also grep existing `.maxpat` files under `patches/` — user-confirmed objects should be added to the appropriate domain file so future lookups succeed. The `live.*` gap this advice was written for is closed: all 30 `live.*` objects documented in the installed bundle resolve, and the 5 with one empty side are label/decorative/source shapes, not gaps.

## maxclass is not authoritative

**The `maxclass` field in the DB is NOT authoritative.** Most MAX objects (`gen~`, `click~`, `expr`, `pack`, `route`, etc.) use `maxclass: "newobj"` with the object name in the `text` field. Only true UI widgets (`button`, `toggle`, `dial`, `meter~`, `gain~`, `ezdac~`, `flonum`, `number`, `scope~`, `spectroscope~`, `levelmeter~`, `multislider`, etc.) use their own name as `maxclass` with no `text` field. The authoritative source is `UI_MAXCLASSES` in `src/maxpat/maxclass_map.py`, NOT the database's `maxclass` field. Setting `maxclass` to a non-UI name causes "invalid attribute maxclass" errors at load.

## Authoritative object names

**The authoritative object name is the refpage's `<c74object name>` attribute, never the filename.** 813 of 2156 bundled refpages disagree: `bitand.maxref.xml` documents `&`, `greaterthan.maxref.xml` documents `>`, `fswap.maxref.xml` documents `swap`, `gswitch2.maxref.xml` documents `ggate`. Any extraction or audit keyed off filenames manufactures 795 phantom "missing from DB" gaps; keyed off the `name` attribute, only 8 installed names fail to resolve (6 documentation pages plus `kbm.data` and `scl.data`; `python3 tools/audit_db.py` recomputes all three figures). **Exception — define-mapped objects:** an object created by a `max define ALIAS TARGET ...;` line in the bundle's `*objectmappings*.txt` files can ship a refpage whose `name` attribute is the implementing class or a typo. Two Max 9.2 cases: `jit.gl.tex2mat.maxref.xml` declares `v8` (the alias is `max define jit.gl.tex2mat v8 jit.gl.tex2mat.js;`) and `jit.unpack.geomat.maxref.xml` declares `jit.unpackl.gl`. For these the alias IS the object name, and the refpage must never be merged into the object its `name` attribute points at (it would write Jitter Tools documentation into core `v8`).

## Refpage placeholders: counts vs types

**Refpages are authoritative for I/O counts far more than for types, and must never overwrite expert overrides.** 640 of 1175 core refpages (54.5%) carry unfilled Cycling '74 template placeholders — `TEXT_HERE`, `INLET_TYPE`, `OUTLET_TYPE`, `undefined`, `Dummy` — with `max-ref` worst at 429/473. `spectroscope~`'s maxref declares 1 outlet typed `OUTLET_TYPE`: the count is right (MAX saves `spectroscope~` as 2 inlets / 1 outlet in every bundle help box) and only the type is a placeholder. `in`'s declares 1 inlet described `Dummy`, which is wrong and is corrected in `overrides.json`. Max 9.2's `jit.web~` refpage types all four outlets `signal`; the help-patch box Max itself serialized says `signal, signal, jit_matrix, ""` — when a refpage and a shipped help box disagree on types, the help box wins. A re-extraction that trusts refpage types would silently revert 36 curated outlets.

## MSP outlets mis-marked as signal

If a control connection from an MSP object's non-primary outlet is flagged by validation (a proposed removal), the DB likely mis-marks that outlet as signal (bulk-extraction bug — many MSP right outlets are actually bangs/floats/indices). Fix the outlet types in `overrides.json` rather than rerouting the patch.

## After a Max update

**After a Max update, re-sync the DB from the installed bundle:** run `python3 tools/audit_db.py` (read-only drift report), then `python3 tools/sync_max_bundle.py` (dry-run: new objects, define aliases, message/attribute deltas), then `--apply new|define --names <explicit names>` and `--apply deltas`, then `--apply groups` (rewrites only `groups.json`), `--apply aliases --names <explicit names> [--shadowed]` for new objectfile shortcuts (`--shadowed` lets an alias replace an RNBO/Gen-only resolution; a name keyed in `overrides.json` `objects` is always aborted, since override keys canonicalise through aliases), `--apply idioms` and `--apply version-io`, then `python3 tools/audit_db.py --help-io --write-baseline tests/fixtures/help_io_baseline.json` (regenerate the help-io baseline; check it shows no regressions), and finally `--refresh-log` so `extraction-log.json` records the sync (the audit's DB-age/drift line reads it). `--min-version N` sets the tag for objects older than the current release; `--apply inherited --attributes <names>` copies named shared Jitter OB3D attributes (defined only in the `jit.group-gl` group page) onto the objects whose refpages list them — only `alpha_mode` has been landed this way. The sync tool is additive and idempotent, never changes existing I/O, and cannot write `overrides.json`. Last synced against Max 9.2.0.
